# 124 — 桌宠前端（Emerald-client）：语音条 UI 解耦 + 自动播放开关

> 来源：茶茶 2026-07-25 反馈。本仓（Emerald-presence）后端已具备的能力见下方「后端现状」，
> 本单要改的代码在前端仓库 `Emerald-client`（与本仓同级目录，见 `docs/dev-environment.md`）。
> 后端如需小改动会在对应小节里标注具体文件。

## 背景

用户反馈两点：
1. 语音条 UI 不好看，且被"抱"在文字消息气泡里——截图显示当前是「播放按钮 + 波形 +
   时长 + 收起文字」全部塞进同一个圆角气泡，文字另起一个气泡在下方。用户想要语音条
   与文字气泡解耦成两个独立元素，不是父子包含关系。
2. 想要一个"自动读语音"开关：开启后角色回复自动播放语音，不用每次手动点。范围覆盖
   聊天框 / 梦境 / 视频通话 / 桌宠四个场景，且要求各自可独立勾选（不是全局单开关）。
   梦境场景特殊：只读正文台词，不读旁白/动作描写（角色心理活动、场景描写等）。
   开启后，视频通话和桌宠的嘴型应该跟着音频波形张合，而不是像现在这样凭文字长度
   估算一个"预计播放时长"来驱动嘴型动画。

## 一、语音条 UI 解耦（组件结构调整）

**现状（截图佐证）**：语音条（播放按钮+波形+时长+"收起文字"）与文字内容被渲染进
同一个消息气泡容器，是父子包含关系。

**要改**：把语音条拆成独立的兄弟元素，不再是文字气泡的子节点。具体视觉方案（是否
保留"收起文字"折叠交互、语音条本身的视觉风格）由前端自行设计，只要求：
- 语音条与文字气泡视觉上是两个独立单元，用户可以一眼看出"这是语音"和"这是文字"
  是并列关系而非包含关系。
- 折叠/展开文字的交互（如果保留）不应影响语音条自身的可点击区域和播放状态。
- 消息时间戳（截图里的"HIM · 02:44 · CALM"）的归属关系同步理一遍，确认它是整条
  消息的元信息还是仅属于某一个子元素。

后端不需要为此改动——语音已经是独立的 `sticker`/语音 payload 广播（见 `channels/registry.py`
`broadcast()` 和 `channels/desktop_ws.py`），UI 解耦纯粹是前端渲染层的事。

## 二、自动播放语音开关

### 后端现状（已具备，可直接复用）

- `admin/routers/settings_misc.py` 已有 `GET/POST /settings/tts-desktop`，控制
  `config.yaml` `tts.desktop_enabled`（当前语义是"桌面语音条总开关"）。
- `POST /tts/synthesize`：为桌面消息按需合成语音（当前是手动点播的入口）。
- `core/output/voice_adapter.py` 的 `synthesize(text, emotion)` 已支持按情绪切参考音色
  （`tts.emotions` 配置块），TTS provider 已支持 GSV 与 openai_compatible 两种（本轮
  cc-tasks/103 系列之外新补的能力，见 `docs/model-presets.md` 或直接看
  `core/output/voice_adapter.py` 顶部注释）。

### 需要的改动

**后端（本仓，小改动）**：
1. `tts.desktop_enabled` 目前是单一布尔值，语义太粗（只区分"桌面语音条开不开"）。
   建议扩展为按场景的开关组，例如：
   ```yaml
   tts:
     auto_play:
       chat: false
       dream: false
       video_call: false
       desktop_pet: false
   ```
   新增 `GET/POST /settings/tts-auto-play` 端点（复用 `settings_misc.py` 现有模式），
   四个场景各自可读写。`desktop_enabled` 保留做向后兼容（映射到 `desktop_pet`
   字段，避免破坏现有前端）。
2. 梦境场景"只读正文不读旁白"：确认 dream 回复文本在下发给前端时，正文台词与
   旁白/动作描写是否已经是结构化分离的字段（搜 `core/stage/dream_runtime.py`
   `DreamStageCharacterView`、`core/dream/` 下的输出格式）。如果当前 dream 回复是
   夹杂旁白的单一字符串，需要新增一个"纯台词"字段供前端 TTS 使用，或者前端自己按
   现有的旁白标记（如括号）做一次和 `_send_tts` 里 `_clean = re.sub(r'（[^）]*）'...)`
   同款的清洗（`core/pipeline.py::_send_tts`）——**优先复用后端这份清洗逻辑而不是
   前端另起一份**，避免两处标记规则走漏。具体方案施工前先读
   `docs/stage.md` §六 Dream Stage 一节确认当前 dream 输出结构。

**前端（Emerald-client）**：
1. 四个场景（聊天框/梦境/视频通话/桌宠）各自的设置开关 UI，读写上面的
   `/settings/tts-auto-play`。
2. 自动播放触发点：收到新的 assistant 消息且对应场景开关为开时，自动调用现有的
   语音获取/播放流程（复用 `/tts/synthesize` 或已有的语音 payload 广播），不需要
   用户手动点。
3. **嘴型驱动方式切换**：现状是"凭文字长度估算播放时长"去跑嘴型动画；开启自动
   播放后，视频通话/桌宠应改为**读音频实时振幅**驱动嘴型张合（Web Audio API
   `AnalyserNode` 取实时波形/音量包络，映射到嘴型开合幅度），而不是预估时长后按
   固定曲线播动画。这样即使 TTS 语速/停顿不均匀，嘴型也能对上实际声音节奏。
   建议做成音频驱动为主、文字估算为 fallback（音频加载失败/自动播放被浏览器拦截等
   场景下退回旧逻辑，不要让功能整体失效）。

## 验收
- 语音条视觉上与文字气泡解耦，折叠交互不受影响。
- 四个场景开关独立生效，关闭的场景不自动播放。
- 梦境模式下自动播放只读台词，不读旁白。
- 视频通话/桌宠开启自动播放后嘴型跟随音频振幅而非固定估时曲线。
- 后端新增的 `/settings/tts-auto-play` 端点若涉及落盘状态，需有观测端点或至少能
  在 `GET /settings/tts-auto-play` 里读回当前值（强制规则 7 的最小版本）。

# Brief 135 - MCP 批量授权与权限体验简化

## 一、背景与已确认问题

当前 MCP 管理页把同一个管理员授权决定拆成了两步：

1. 勾选工具并保存 `allow_tools`；
2. 再逐个工具选择并保存 `tool_policy.effect`。

当 `mcp_servers.require_local_policy: true` 时，仅进入 `allow_tools`、但没有本地
`tool_policy` 的工具会保持 `pending_confirmation`，运行时不会注册进
`_TOOL_REGISTRY`，因此角色拿不到工具 schema。

现有 URL 导入流程会为选中的工具自动生成默认 policy，但已导入 server 的手工白名单
更新不会补齐 policy。管理页仍提示“已保存并热重载”，形成配置保存成功、角色实际不可见的
假成功体验。

另外，现有页面宣称“空 allow_tools = 全部允许”的兼容语义，但严格本地策略要求
`allow_tools` 非空。管理面展示、配置校验和运行时行为不一致。

## 二、产品决策

PresenceKit 是本地单用户系统。MCP 权限模型保留 server 级本地管理员授权边界，但不再要求
管理员逐工具完成重复确认。

新增两个 server 级批量按钮：

### 1. 一键默认授权

作用于当前 server 本次 `list_tools()` 已发现的全部工具，一次完成：

- 全部加入 `allow_tools`；
- 已有显式 `tool_policy` 原样保留；
- 仅为缺失 policy 的工具写入默认策略；
- 使用现有 `suggest_tool_policy()` 与导入默认逻辑：可可靠判断为只读的工具落为 `read`；
  其他工具落为 `write`，语义未知或高风险时 `require_confirm: true`；
- 保存、配置热重载和返回有效状态必须是一次原子操作。

这是常规推荐入口。管理员不需要再逐个点击“保存模式”。

### 2. 一键无限制授权

作用于当前 server 本次已发现的全部工具，一次完成：

- 全部加入 `allow_tools`；
- 所有工具的 policy 覆盖为：

```yaml
effect: unrestricted
idempotent: true
require_confirm: false
```

- 允许覆盖已有逐工具策略；
- 点击后只做一次明确的浏览器确认，确认文案说明：工具可以修改外部状态、不会逐次请求确认，
  同一 `request_id` 在断连场景最多重试三次；
- 确认后一次保存并热重载，不再逐工具确认。

现有中文“无权限”容易被理解为“禁止访问”。界面统一改称“无限制”，英文仍为
`unrestricted`。不得把此模式命名为“无权限”或“免权限”。

### 3. 个别例外

保留现有逐工具模式选择，供管理员在批量授权后调整少数例外。逐工具保存不再是工具进入
白名单并对角色可见的必经步骤。

## 三、后端实现要求

主要文件：

- `admin/routers/settings_mcp.py`
- `core/mcp_client.py`（仅在需要复用/收口策略 helper 时修改）

新增 server 级批量授权 API。可以扩展现有 `PATCH /settings/mcp/{name}`，也可以新增明确的
子资源端点，但必须满足：

- 请求只接受枚举动作 `default` / `unrestricted`，不接受任意 method、命令或远端 URL；
- 工具集合来自当前已连接 server 的运行时 `list_tools()` 快照，不信任前端提交的任意工具名；
- server 未连接、运行时没有有效工具目录或配置已被删除时，返回明确的 `409`，不得写入半成品；
- 单次请求内同时更新 `allow_tools` 与完整 `tool_policy`；
- 写入前通过 `validate_local_tool_policy(..., required=True)`；
- 写入、`config_loader.reload_config()`、定点热重载沿用现有 MCP 设置链路；
- 返回 `reload_status`、最终 `allow_tools`、policy 状态和已处理工具数量；
- 热重载失败时配置可以保留，但必须返回 `restart_required`，管理面明确提示；
- 不记录工具参数、返回正文、完整 URL、headers 或凭证。

把“导入时生成默认 policy”和“一键默认授权”的策略生成收口到同一个 helper，禁止两套规则
继续漂移。

## 四、修复普通保存的假成功

普通 server “设置”保存仍允许只改启停、代理或白名单，但必须消除以下假成功：

```text
allow_tools 已包含工具
但严格模式下缺少 tool_policy
API 仍返回已热重载成功
角色实际看不到工具
```

采用以下语义：

- 当请求新增白名单工具且严格模式开启时，后端自动为新增工具补默认 policy；
- 已有显式 policy 保留；
- 移出白名单的 policy 继续清理；
- 更新后的每个 allowlisted 工具都必须有有效 policy，才允许写入；
- API 返回后不得存在 `allowlisted=true`、`policy_status=pending_confirmation` 的新增工具。

这意味着普通“勾选 + 设置”本身也应足以让工具注册并对角色可见。批量按钮是效率入口，不能
成为修复一致性的唯一入口。

## 五、统一空白名单语义

在严格策略模式下，统一为：

```text
allow_tools: [] = 不授权任何工具
```

不得继续显示或实现“空 = 全部允许”。需要同步修改：

- MCP 管理页提示；
- `_server_view()` 的 `allowlisted` / `policy_status` 计算；
- 严格模式校验与运行时注册语义；
- `docs/tools.md` 与 `docs/feature-control-surface.md`。

旧的非严格 legacy 模式可以保留“空 = 全部”兼容行为，但管理页必须根据
`require_local_policy` 返回值显示准确文案。`GET /settings/mcp` 需返回该布尔字段，前端不得猜测。

## 六、前端要求

主要文件：

- `admin/static/js/mcp.js`
- `admin/static/pages/mcp.html`（仅在需要静态容器或文案时修改）

每个已连接 server 的工具区增加：

- `默认授权全部` 按钮；
- `无限制授权全部` 按钮；
- 批量执行结果摘要：处理数量、默认/无限制模式、热重载或需重启；
- 当没有发现工具或 server 未连接时禁用按钮并显示原因。

交互要求：

- 默认授权无需逐工具确认；
- 无限制授权只弹一次确认；
- 请求执行期间按钮禁用，防止重复提交；
- 成功后重新读取 `/settings/mcp`，以服务端最终状态重绘；
- 不在浏览器端循环调用逐工具保存 API；
- 不用自然语言 toast 掩盖 `pending_confirmation`、`restart_required` 或连接失败；
- 保留逐工具下拉框，批量授权后可继续修改个别工具。

编辑 `admin/static/js/mcp.js` 后，必须按仓库规则更新 `admin/static/index.html` 中对应脚本的
`?v=`。如果修改 `admin/static/pages/mcp.html`，还要更新
`ADMIN_UI_FRAGMENT_VERSION`、`core.js` 的 query version 以及页面 fragment 缓存版本。

## 七、保留的有效安全边界

本工单简化重复授权，不删除以下有效边界：

- MCP 总开关与单 server 开关；
- server 级本地管理员主动授权；
- URL/header 凭证脱敏与 `${ENV_VAR}`；
- 只允许已发现、已注册的动态工具；
- `tool_loop`、角色工具类目、全局 exclude、Self Capability 与 proficiency 等既有暴露面；
- 工具 schema 校验、origin 闸门、action trace 和 API 调用审计；
- `outcome_unknown` 与幂等 request_id 语义。

不得新增没有攻击面对应关系的额外确认层，不得把远端 description/annotation 当成本地授权，
也不得要求用户为同一 server 的每个工具重复确认。

## 八、测试

修改测试前先读 `docs/dev-environment.md`。只跑相关测试，使用仓库规定的并行入口。

至少覆盖：

### 后端

- 默认批量授权把全部运行时工具加入 allowlist；
- 默认批量授权仅补缺失 policy，保留已有显式 policy；
- 未知工具默认 `write + require_confirm: true`；
- 无限制批量授权覆盖全部 policy，并强制 `idempotent=true`、`require_confirm=false`；
- server 未连接或工具目录为空时不写配置；
- 批量请求一次写入并只触发一次定点热重载；
- 热重载失败返回 `restart_required`；
- 普通勾选新增工具时自动补 policy，不再留下 `pending_confirmation`；
- 严格模式空 allowlist 表示零工具；
- legacy 非严格模式兼容行为不回归；
- 未发现工具名不能通过批量端点进入配置；
- API 响应与日志不泄露 URL 路径凭证、headers 或 token。

### 前端

- 每个已连接 server 显示两个批量按钮；
- 未连接/无工具时按钮禁用；
- 默认授权不弹逐工具确认；
- 无限制授权只弹一次确认；
- 请求期间防重复提交；
- 返回 `restart_required` 时明确提示重启；
- 批量完成后按服务端状态重绘；
- 页面不再显示“严格模式空白名单等于全部允许”。

文档写清：

- 默认授权与无限制授权的区别；

## 十、验收标准

以下场景必须成立：

```text
连接一个含多个工具的 MCP server
-> 点击“默认授权全部”一次
-> allow_tools 与完整 tool_policy 同时落盘
-> server 热重载一次
-> 所有工具注册成功
-> 角色在满足既有 tool-loop 暴露条件时立即获得 schema
-> 不需要逐工具点击“保存模式”
```

以及：

```text
点击“无限制授权全部”
-> 只确认一次
-> 所有已发现工具进入 allowlist
-> 所有 policy 为 unrestricted + idempotent
-> 不再逐次请求 effect/confirmation
-> 页面准确显示无限制状态与风险说明
```

不得出现：

- 页面显示白名单已保存，但工具仍因缺少 policy 未注册；
- 严格模式把空 allowlist 当作全部允许；
- 前端逐个发送 N 次策略请求；
- 批量授权接受当前 server 未发现的工具名；
- 将远端 annotation 直接视为本地授权；
- 日志、响应、测试 fixture 或文档写入真实 token、完整敏感 URL 或本机绝对路径。

## 审计目标

在以下部署形态下判断功能是否真实成立：

```text
PresenceKit backend 独立运行在本机、NAS 或服务器
Desktop 客户端可完全不启动
Mobile 仍可独立完成其承诺能力
```

同时判断 Desktop 和 Mobile：

1. 哪些能力应当对应；
2. 哪些差异是设备形态导致的合理差异；
3. 哪些是手机未接完；
4. 哪些只是 UI 展示债务；
5. 哪些入口看起来可用，实际依赖桌面、本地文件或错误状态；
6. 哪些后端能力已经存在，但前端没有入口；
7. 哪些前端功能维护了第二套业务真值。

## 第二部分：后端独立运行审计

逐项确认 Mobile 是否直接依赖：

* Desktop WebSocket 在线；
* desktop channel active；
* `channel_queue.json`；
* Tauri command；
* Desktop 本机文件；
* Windows 路径；
* Desktop localStorage；
* Desktop 生成的配置文件；
* Desktop 先执行过某个激活操作；
* Desktop 负责注册某个 Backend channel；
* Desktop 独有 token 或 scope。

区分：

```text
名字里叫 desktop，但实际是公共后端契约
```

和：

```text
真正依赖 Desktop 客户端进程
```

发现依赖时给出真实文件路径和调用链，不凭命名判断。

## 第三部分：跨端同步语义

审计以下矩阵：

### Desktop 发消息

* Desktop 如何收到 reply；
* Mobile durable queue 是否收到同一 assistant turn；
* turn_id / msg_id 是否一致；
* Mobile 前台与后台如何去重；
* 用户消息是否会实时同步到 Mobile；
* 若不会，是否通过历史刷新补齐。

### Mobile 发消息

* Mobile 如何收到同步 reply；
* Desktop 在线时是否收到 assistant reply；
* Desktop 是否会显示 Mobile 发出的 user bubble；
* 若不会，当前是否属于明确契约；
* history reload 后两端是否最终一致。

### Proactive turn

* Desktop 在线；
* Desktop 离线；
* Mobile 在线；
* Mobile 离线；
* 两端均离线。

明确区分：

```text
assistant turn 跨端同步
user bubble 跨端实时镜像
最终历史一致
```

不要混为同一能力。

## 第四部分：UI 债务

重点找：

* 显示成功但业务失败；
* 空数据被显示成正常；
* 只读能力看起来可编辑；
* 本地 override 掩盖后端真值；
* 同一设置在多个页面重复；
* 保存后不生效却没有提示；
* 入口存在但调用未实现；
* Debug 功能暴露成普通用户功能；
* 旧命名让用户误解依赖关系；
* 状态加载失败后继续显示旧数据；
* 一个超大 AppShell 同时持有太多业务状态；
* 页面进入时重复请求或并发启动；
* 长任务没有明确 loading / cancel / error；
* Desktop 已成熟但 Mobile 仍是临时弹窗；
* Mobile 原生能力已存在但 Flutter UI 无入口。

每项输出：

```text
文件路径
当前表现
真实后端状态
用户风险
优先级 P0 / P1 / P2
最小修复
是否需要设计决策
```

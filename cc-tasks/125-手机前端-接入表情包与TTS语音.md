# 125 — 手机前端：接入表情包 + TTS 语音

> 来源：茶茶 2026-07-25 反馈。手机前端是轮询式通道（`channels/mobile.py`
> `MobileChannel`，非 WebSocket），本单盘点后端现状 + 需要的后端补丁 + 前端要做的事。

## 背景

表情包与 TTS 语音目前只在 QQ（表情包+语音）和桌宠（表情包，语音走独立的按需合成
接口）上有落地，手机前端完全没接入。用户要求手机前端也支持表情包与语音播放，并且
要有对应的设置开关和 UI（不能默认打开占带宽/流量却没得关）。

## 一、后端现状盘点

### 表情包：后端已就绪，前端未接
`core/output/sticker.py::maybe_send_sticker()` 在选中表情包后会调用
`channels.registry.broadcast(sticker=payload, exclude_channels={"qq"})`，`MobileChannel.send()`
/ `send_with_behavior()` 都接受 `sticker` 参数并写入轮询队列（`channels/mobile.py`
`_write_to_queue()`，`item["sticker"] = sticker`；已有测试
`tests/test_sticker_broadcast.py::test_sticker_payload_reaches_desktop_ws_and_mobile_queue`
覆盖这条链路）。`payload` 结构是 `{"kind": "sticker", "emotion": "...", "data_url":
"data:image/...;base64,..."}`，自包含（不暴露本机文件路径），前端拿到直接能渲染。

**结论**：表情包后端到手机轮询队列这一段是通的，纯粹是前端从未读取/渲染
`sticker` 字段。

### TTS 语音：后端目前没有推送到手机的路径，需要后端补一段
`core/pipeline.py::_send_tts()` 合成语音后只调用了 `core/output/voice_adapter.py
send_voice()` → `qq_adapter.send_record()`，这条路径**只发 QQ**，没有像表情包那样
经过 `channels.registry.broadcast()`。桌宠拿到语音走的是另一条独立的按需接口
`POST /tts/synthesize`（`admin/routers/settings_misc.py`），是"前端主动请求合成"
模式，不是推送。

**手机是轮询通道，两种模式都能接，各有取舍**：
- 方案 A（跟表情包一致，推送进队列）：`_send_tts` 成功合成后，把音频转 base64 塞进
  `channels.registry.broadcast()` 的一个新 kwarg（如 `voice={"data_url": "data:audio/wav;base64,...",
  "emotion": ...}`），`MobileChannel` 照抄 sticker 的写入方式存进队列条目。优点是
  跟表情包同一套心智模型，缺点是音频通常比表情包图片大不少，轮询队列文件会明显
  变大（`channels/mobile.py` 的队列是落盘 JSON，见 `_load_queue`/`_prune_queue`）。
- 方案 B（复用现有按需合成接口）：手机轮询到一条新消息后，如果本地设置开启了
  "自动播放语音"，客户端自己再发一个请求（类似 `/tts/synthesize`，需要按 message_id
  或者直接传文本）去按需拉音频，不在轮询响应体里塞音频本体。优点是队列体积不受
  影响、行为跟桌宠现有模式一致，缺点是多一次往返。

**建议方案 B**，与桌宠当前"按需合成"模型保持一致，减少两套心智模型并存的复杂度；
若手机端后续做成 WS 常驻（脱离轮询）再统一切到推送模式。具体选型请与用户/前端
一起拍板，不在本单强行下结论。

## 二、后端要做的事（本仓）

1. 若采用方案 B：确认 `POST /tts/synthesize` 能否直接被手机端复用（当前实现是否
   绑定了桌宠专属的鉴权 scope 或参数假设，见 `admin/routers/settings_misc.py`
   `synthesize_desktop_tts`）；如果绑得太死，拆一个通用版本或放宽鉴权 scope。
2. `channels/mobile.py` 轮询队列条目里补充"这条消息是否有可用语音"的轻量标记
   （不放音频本体），供客户端判断要不要发起按需合成请求。
3. 手机侧设置开关（表情包总开关 + 语音自动播放开关）参照 `admin/routers/settings_misc.py`
   `/settings/tts-desktop` 现有模式新增对应端点，或并入 124 号单里新设计的
   `/settings/tts-auto-play`（如果按场景拆分，手机可以算其中一个场景维度）。

## 三、前端要做的事（手机前端仓库）

1. 轮询响应里读取 `sticker` 字段并渲染（图片已经是 base64 data URL，直接可用，
   不需要额外请求）。
2. 语音播放 UI：参照 124 号桌宠单的语音条解耦要求，同样不要把语音条塞进文字气泡
   容器。
3. 设置页新增两个开关：表情包接收开关、语音自动播放开关，默认关闭（避免手机流量/
   存储被意外占用），读写对应后端端点。
4. 语音自动播放开启时的触发逻辑与音频获取方式，按后端最终选定的方案 A/B 对接。

## 验收
- 手机端能收到并渲染表情包（复用现有广播链路，理论上后端不用改就能验证这一半）。
- 语音开关关闭时完全不产生语音相关流量。
- 开启后能听到语音，且 UI 上语音条与文字气泡是独立元素。
- 新增/调整的后端端点补齐观测端点或至少可读回配置值（强制规则 7 最小版本）。

请修复 Self Capability P0 的 autonomy runner 接入缺失，并补上 autonomy 工具 allowlist 的执行期强制校验。

这是修复工单，不扩展 capability 范围，不修改全局 MCP、tool policy、feature flag 或传统 scheduler。

## 已确认问题

1. 普通对话可以调用 `manage_self_capability`。
2. autonomy runner 没有把 Self Capability gateway 加入 schema，也没有注入 capability context/revision。
3. autonomy 工具执行固定使用 `origin="autonomy_loop"`，无法通过 Self Capability gateway 的 origin 校验。
4. autonomy allowlist 目前只限制模型可见 schema，收到 tool call 后没有再次校验工具名，异常或幻觉调用仍可能进入 dispatcher。
5. 被 dispatcher 拒绝的调用可能被 runner 当作普通工具结果，最终错误记成成功的 `tools_only`。
6. 缺少“内部唤醒修改 capability，并影响后续 MCP 可用性”的端到端测试。

## P0.1 修复目标

实现以下闭环：

```text
autonomy wake
→ 读取当前 Self Capability 状态与 revision
→ 按条件暴露 manage_self_capability
→ 模型请求修改
→ 以 autonomy_self_management origin 执行
→ 重新加载 effective capability
→ 刷新本轮后续工具 schema / allowlist
→ 后续工具调用使用新状态
→ run、审计和 MCP 调用可以关联
```

## 一、先修执行期 allowlist

在 autonomy runner 收到每一个 tool call 后、调用 dispatcher 前，必须重新校验：

```text
requested_tool_name in current_effective_allowlist
```

不能只依赖传给模型的 schema。

要求：

* 未在 allowlist：fail-closed，不进入 `tool_dispatcher.execute()`
* 写入明确的拒绝记录
* 不把拒绝伪装成普通工具成功
* 不将该工具计入成功执行工具列表
* 不允许已注册但未授权的 builtin、MCP 或 Self Capability 工具通过
* 校验使用当前步骤最新的 effective allowlist，而不是 run 开始时永久冻结的副本

建议增加明确状态，例如：

```text
tool_call_denied
reason = not_in_autonomy_allowlist
```

不要使用自然语言文本是否包含“拒绝”来判断成功或失败。

## 二、接入 Self Capability gateway

只有满足以下条件时，autonomy schema 才加入：

```text
manage_self_capability
```

条件至少包括：

* 当前 uid + char_id 存在 `mutable_by_agent=true` 的 grant
* capability registry 中存在对应项
* 当前运行未被系统策略禁止 self-management
* gateway 本身已注册且可用

给模型注入安全摘要，至少包括：

```text
current_revision
mutable capabilities
current agent-selected value
effective value
constraints
locked status
```

不得注入：

```text
MCP URL
headers
Bearer Token
API Key
config.yaml 内容
其他 uid / char_id 状态
全局管理配置
```

身份必须来自 autonomy job 的可信上下文。模型不得提供或覆盖 uid、char_id。

## 三、正确使用 origin

普通业务工具继续使用：

```text
origin="autonomy_loop"
```

只有 `manage_self_capability` 使用：

```text
origin="autonomy_self_management"
```

不要把整个 autonomy run 都改成高权限 origin。

不要复用：

```text
admin_console
assistant_self_management
```

dispatcher 仍需验证工具名与 origin 的合法组合。`autonomy_self_management` 不得执行普通工具或任意 MCP 工具。

## 四、本轮动态刷新

成功执行 `manage_self_capability` 后：

1. 重新读取 Self Capability store。
2. 验证 revision 已更新。
3. 重新计算 effective capability。
4. 重新计算 autonomy effective allowlist。
5. 更新下一步发送给模型的工具 schema。
6. 后续 tool call 必须使用新 allowlist 再次执行期校验。

预期语义：

* 本轮 disable 某工具：后续步骤立即不可调用。
* 本轮 enable 某个已经全局可用、已注册、已授权且满足 autonomy policy 的工具：后续步骤可以调用。
* MCP Server 未连接、工具未注册、proficiency 不允许或 `mcp_explicit` 不满足时，仅 enable capability 不得使其可执行。
* 修改 `autonomy.enabled=false` 后，不要粗暴中断正在持久化的当前动作；完成当前 Self Capability 操作和审计后，停止本轮继续调用普通工具，并阻止后续 wake。
* 修改 interval 只影响后续调度，不重新安排已经领取的当前 job。

为避免 schema 与执行权限不一致，建议 autonomy loop 每一步重新构造当前工具 schema，而不是只在 run 开始时构造一次。

## 五、结果语义修复

runner 必须区分：

```text
tool_executed
tool_failed
tool_call_denied
self_capability_changed
self_capability_rejected
```

以下情况不得被记录为成功的 `tools_only`：

* 工具不在 allowlist
* origin 不允许
* capability 未授权
* capability 被锁定
* revision 冲突
* 参数越界
* dispatcher fail-closed
* MCP 工具当前不可执行

run 的最终 disposition 应能反映：

* 是否产生实际工具副作用
* 是否只修改了 Self Capability
* 是否所有调用都被拒绝
* 是否因修改 `autonomy.enabled=false` 主动停止

不要通过解析 dispatcher 返回的自然语言文本判断成功。

## 六、关联审计

为同一次 autonomy run 贯通以下标识：

```text
run_id
job_id
self_capability action_id
tool action trace / MCP api call audit id
```

Self Capability 审计 UI 补充显示：

```text
source
capability_id
revision_before
revision_after
old agent value
new agent value
old effective value
new effective value
action_id
result / rejection reason
```

对于拒绝请求也必须保留可查询审计：

* not_granted
* immutable
* locked
* revision_conflict
* out_of_range
* unavailable
* invalid_action
* not_in_autonomy_allowlist

不得记录 secret 或完整 MCP 参数。

## 七、工具决策矩阵

在 autonomy 管理页增加只读决策矩阵，至少展示：

```text
工具名称
全局 enabled
是否已注册
MCP server connected
MCP allowlist / policy
MCP proficiency
Self Capability granted
Agent selected
Self Capability effective
autonomy tools allowlist
mcp_explicit
effect / dangerous / require_confirm
最终是否进入 schema
最终是否允许执行
拒绝原因
```

不要只显示“已启用工具”。

所有字段使用安全摘要，不显示连接凭证、完整 URL 或 headers。

## 八、测试

至少新增以下测试：

### 执行期安全

* schema 中没有的已注册工具被模型幻觉调用时，runner 在 dispatcher 前拒绝
* 不在 autonomy allowlist 的 builtin 工具被拒绝
* 不在 autonomy allowlist 的 MCP 工具被拒绝
* 普通 `autonomy_loop` origin 无法调用 `manage_self_capability`
* `autonomy_self_management` origin 无法执行普通或 MCP 工具
* 被拒绝调用不会记为 `tools_only` 成功

### Self Capability 接入

* 有 mutable grant 时 schema 包含 gateway 和 revision/context
* 没有 mutable grant 时不暴露 gateway
* 模型不能通过参数伪造 uid 或 char_id
* autonomy 成功 disable 工具后，本轮下一步立即无法调用
* autonomy 成功 enable 已授权 builtin 后，本轮下一步可以调用
* autonomy 成功 enable 已授权 MCP capability 后，只有 MCP 已注册、连接、proficiency 和 mcp_explicit 均通过才可调用
* revision 冲突失败并留下拒绝审计
* locked / immutable / not_granted / out_of_range 均失败并留下拒绝审计
* 修改 `autonomy.enabled=false` 后当前 run 安全收尾，后续 wake 被阻止
* 修改 interval 仅影响后续调度

### 隔离与关联

* 不同 uid 隔离
* 不同 char_id 隔离
* 叶瑄修改不影响 hongcha 和 yexuan_j5412
* run_id、job_id、Self Capability action_id、后续 MCP 调用记录可以关联
* 审计和 UI 不泄露 URL、Token、headers

必须包含至少一个完整端到端场景：

```text
autonomy wake
→ manage_self_capability(enable mcp.use:X/Y)
→ 动态刷新 schema
→ 同一 run 后续调用 MCP Y
→ run / capability audit / MCP audit 关联成功
```

以及反向场景：

```text
autonomy wake
→ disable mcp.use:X/Y
→ 同一 run 后续尝试调用 Y
→ 执行期 allowlist 拒绝
→ 不进入 dispatcher / MCP
→ run 不记为工具成功
```

## 九、边界

本工单不得：

* 给 Agent admin token
* 调用管理 API
* 直接写 config.yaml
* 修改 MCP Server lifecycle
* 修改 MCP allow_tools / tool_policy
* 修改 effect / confirmation
* 修改传统 scheduler
* 新增任意配置写工具
* 扩充 Self Capability registry 范围
* 用字符串匹配代替结构化执行结果
